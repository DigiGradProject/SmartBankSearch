# III. Framework

The implemented framework provides Arabic–English retrieval-augmented search over National Bank of Egypt website content. It combines multilingual representations, lexical retrieval, domain-aware ranking, and evidence-based answer eligibility. A React interface communicates with a FastAPI service, which coordinates query understanding, retrieval, context construction, and local language-model inference through Ollama. The design preserves the original question while constructing a separate search query and records retrieval decisions, confidence explanations, and source information for inspection.

**Architecture and knowledge representation.** The offline pipeline cleans website documents, normalizes Arabic text, and creates section-aware parent and child chunks. Under the current defaults, parent sections have an approximate 800-token budget, while indexed child windows use up to 280 approximate tokens with 50-token overlap. These are implementation budgets rather than measurements with the embedding model’s tokenizer. Child chunks are preferred for indexing. Records retain document identifiers, source URLs, language, product family, document type, section information, and parent references. BGE-M3 generates dense vectors and sparse lexical weights. Dense vectors and metadata are persisted in a cosine-distance Chroma collection; a separate BM25 index stores tokenized titles and text. Content hashes support idempotent updates. The online service retrieves this evidence before deciding whether an answer can be produced.

**Query understanding and retrieval.** Query preparation resolves language, normalizes text, classifies intent, extracts entities, and applies expansion and rewriting. Critical deterministic rules precede semantic intent classification. BGE-M3 intent prototypes provide the semantic signal, with regular-expression fallbacks and a general-query route when evidence is weak. Both evaluation modes retain this preparation, including intent-dependent query expansion. In the API path, a planner can split questions expressing distinct intents into at most two subqueries and merge their retrieved evidence; the retrieval-mode evaluator measures individual calls to the search service rather than this complete API path.

Candidate retrieval combines two ranked channels. The vector channel obtains up to 50 cosine-nearest candidates and rescores them using dense similarity and BGE-M3 sparse overlap, with a default dense weight of 0.7. The lexical channel retrieves up to 50 positive-scoring BM25 matches. Reciprocal rank fusion combines their chunk identifiers:

\[
\operatorname{RRF}(d)=\sum_{c\in\{\mathrm{vector},\mathrm{BM25}\}}\frac{1}{60+r_c(d)},
\]

where ranks start at one and absent documents contribute zero. The implementation scales fused scores by 30 and caps them at one. With the current settings, up to 32 candidates enter subsequent processing. Low-value and navigation-heavy material is filtered, keyword relevance adjusts ordering, and BGE-reranker-v2-m3 reranks a pool of up to 20 candidates, retaining five. Enterprise category, metadata, and product-family adjustments operate before and after cross-encoder reranking; they reorder retrieved evidence without injecting a canonical document.

The `ENTERPRISE` mode additionally permits intent-conditioned metadata filtering and the answer gate. When filtered retrieval produces too few candidates, the hybrid retriever executes related-type expansion and, if necessary, broader language-restricted retrieval. The mode named `PURE_SEMANTIC` disables enterprise filters, business-rule adjustments, and confidence-based abstention. It still includes BM25, sparse rescoring, query expansion, keyword ranking, and the cross-encoder. Consequently, it is a hybrid baseline without enterprise controls, rather than a dense-only semantic baseline. BM25 tokenization selects Arabic or Latin tokens according to the resolved language; mixed-language lexical coverage is therefore not guaranteed.

**Decision engine.** The decision engine emits `ANSWER`, `NO_ANSWER`, or `RETRY_RELATED`. Empty evidence yields `NO_ANSWER`. If intent confidence is at least 0.90 and the first result does not match the expected family through document type, URL markers, or category, the engine emits `RETRY_RELATED`. Otherwise, confidence below 0.42 causes abstention, while sufficiently confident, family-compatible evidence—or a general FAQ intent—permits an answer. Remaining family mismatches also abstain. The deprecated `FORCE_CANONICAL` value is retained for compatibility but is not emitted. Crucially, the present API treats `RETRY_RELATED` as a non-answer outcome; it does not execute another retrieval in response to that label. Executed broadening belongs to the earlier hybrid retrieval stage and should not be conflated with a post-decision retry loop.

**Confidence and answer construction.** Confidence is an engineered evidence score, not a demonstrated probability of correctness. Its core combines intent confidence, the first final ranking score, the mean of the first five scores, category consistency, score agreement, and source diversity, with respective weights 0.15, 0.25, 0.15, 0.20, 0.15, and 0.10. Small legacy contributions supplement this core, and high-confidence intent–metadata disagreement reduces the component score by a factor of 0.55. Retrieval then blends this result at weight 0.75 with a legacy score at weight 0.25; the latter combines mean top-three relevance and maximum top-five keyword overlap at weights 0.55 and 0.45. Final ranking scores can already contain enterprise adjustments, so they are not independent raw dense, BM25, or cross-encoder measurements.

For eligible requests, the API can use specialized answer builders or construct a compressed context with an approximate 2,000-token budget and up to three citations. The generative path calls a configured Qwen3 model with instructions to use retrieved evidence, with extractive fallback where applicable. A separate faithfulness check can trigger one stricter regeneration for an unsupported answer; failed regeneration or a second unsupported result causes abstention. This generation retry is distinct from retrieval retry. Retrieval-only validation measures ranking and an implementation-specific confidence proxy; it does not establish factual-answer accuracy, probability calibration, or code-switching robustness.
